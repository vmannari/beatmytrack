## Authority and recovery policies

Schema `0015_exception_recovery` adds nullable refresh operation hashes/nonces/replacement/time and server-owned resume abandoned/settled/refunded state. Back up and migrate before matching API/worker/client rollout. No existing installation was migrated. Downgrade must use a matching backup rather than discarding refund/recovery state.

Refresh recovery is a narrow application protocol: both the previous refresh secret and the independent private operation secret are required within 120 seconds (configuration maximum 300), with a live, unconsumed replacement in the same session family. Server credentials are derived with domain-separated HMAC-SHA256 and a fresh server nonce; only hashes/nonces are stored. Family-first locking plus conditional token consumption preserves one replacement across PostgreSQL and SQLite concurrent retries. A different operation still detects reuse and revokes replacements. Legacy requests keep strict rotation.

This is not DPoP or a claim of protection against theft of the complete private credential/operation pair. TLS, private application storage, no credential logging, short recovery windows and ordinary reauthentication remain necessary. The security tradeoff is explicit and tested; [RFC 9700 refresh protection](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14) explains why rotation/reuse detection must remain.

Resume recovery returns a banked credit only for the requested unsettled spend after the whole unsubmitted attempt becomes permanently ineligible for online submission. It restores the same-day free allowance only within its UTC day; expired daily resources never roll over, and temporary ad_preview receipts never mint banked rewards. Confirmation records a delivered spend; a confirmed receipt is not refunded. Player→ticket→race locking makes submission and abandonment mutually exclusive. The original timeline/three-resume/exact-receipt rules remain.

Modern unresolved recovery evidence is protected until resolution. Bounded retention batches close expired unsubmitted uncertainty older than the retention interval, return eligible banked resources and mark the receipt settled before pruning. This avoids permanent lost-device evidence growth. Legacy spends are already settled and retain their earlier semantics. Production ad/purchase fulfillment remains unconfigured.

Completed recordings cannot be persisted to a full/unwritable device. While the app stays alive, the new service retains failed data and exposes recovery regardless of navigation. Hard process termination before any durable write can still lose that recording; in-progress race persistence was not added. The UI states that unsaved recovery requires keeping the app open. Memory reservation limits apply to verified attempts; the existing offline race choice preserves unlimited ordinary racing.

Cloud compatibility must use a consistent capability floor or versioned routing and retain original-build workers for accepted cohorts. Transport fallback never changes physics/rules or score keys. Unsupported original cohorts retain explicit retry/support status; they are not silently rescored. API readiness, worker capability/progress and a verified synthetic/private workflow remain distinct operational checks.
