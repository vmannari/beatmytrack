# Backend scalability repairs and capacity tooling

Owner request: fix all P1/P2 findings in [the October 4 review](BACKEND_SCALABILITY_REVIEW_2026_10_04.md), and add load tooling/tests. Requirements: B01–B07, B19–B20, B23, WR03–WR08, RW05–RW07 and Q01. Source changes only; existing PC services, player data, NAS and production were not migrated/restarted/deployed. Rules v18, physics 0.50 and the complete canonical 120 Hz input timeline are unchanged.

## Repairs

| Review item | Implemented behavior |
| --- | --- |
| 1 / P1 storage and worker failure | Worker object volume is writable. Ghost durability happens outside run/group/PB locks. Infrastructure faults retry durably; a finalization failure leaves a fenced lease recoverable. Main worker loops survive failed iterations. |
| 2 / P1 verification capacity | One reusable pinned engine per worker, eight immutable compiled tracks cached, fresh simulation/session/ghost state each job, job-token fences, bounded diagnostics/deadline and recycling after 100 jobs. Ordinary public PB jobs skip optional ghosts. Independent worker processes can scale separately. APIs warm their immutable contract before accepting concurrent races. |
| 3 / P1 queue contention | Trigger-maintained global/per-player pending counts replace historical COUNT scans. Claims update per-player fairness timestamps, without locking a global queue row. Blob publication and validation happen outside admission/write locks. Admission is a short serialized transaction preserving hard capacity. |
| 4 / P1 matching | Exact distinct eligible finishers and tick-frequency projections; two skill queries over at most 20 indexed compatible boards. SQL applies compatibility/latest-version predicates before limits. Matching selects a bounded random ID window and decodes five metadata rows before cohort locking. Membership plus a recoverable retry marker commits before snapshot construction; interrupted retries complete one frozen response. |
| 5 / P2 snapshots | Four batched snapshot queries, no writer locks on GET, coherent PostgreSQL read snapshots, conditional responses with changing server time in a header. Auth, membership, account bans and track availability are rechecked before 304. |
| 6 / P2 communication | Gzip responses/uploads, lossless six-byte input frames inside base64, versioned schema, conditional snapshot/document cache, batched owned run statuses, shared result status, 2.5–5 second jittered polling, 20-card discovery/search pages loaded on demand. New transport/polling is negotiated through bootstrap, preserving operation against an older backend. |
| 7 / P2 leaderboards | Exact database-maintained population/tick frequencies, indexed keyset cursors with snapshot positions, revision-safe aggregate cache enlarged to 2,048 entries and coalesced cold reads. Histograms/rank prefixes operate on tick frequencies rather than whole player populations. Latest discovery avoids global version aggregation. |
| 8 / P2 memory and rendering | Two large-body slots cover parsing through endpoint completion; compressed and decoded limits, strict gzip/parser bounds. Godot HTTP, replay packing, UTF-8/JSON parsing, cache copies and durable replay IO run in threads while frames yield. Normal results appear immediately while the outbox is saved. |
| 9 / P2 optional ghosts | Prefetch/coalescing, two-second optional request timeout, account/group/vehicle/run-scoped cache with 30-second freshness and byte/entry limits. Race start uses only already recorded/cached poses and never waits for a ghost. |
| 10 / P2 retained evidence/storage | Ninety-day closed-week archival keeps exact scores and membership while releasing weekly replay/ticket links and route previews. Superseded attempts are pruned in bounded batches; public PB/proof evidence and immutable tracks remain. Timestamped retry keys expire safely; legacy keys and permanent grant identities remain. DB publication/read pins coordinate online GC; online backups pause only GC, then stream a consistent DB dump and immutable objects. Local gzip objects and an explicit HTTPS S3-compatible adapter support migration. |
| 11 / P2 role/NAT budgets | Configurable API pool 4, worker pool 2, zero overflow, three-second acquisition/connect deadlines and PostgreSQL statement/lock deadlines. Validated per-player weighted budgets preserve a separate generous edge budget for shared NATs. Public uploads always enter durable validation; synchronous validation requires an explicit non-production test/development setting. Storage reads release snapshot connections before pin/IO. |
| 12 / P2 SQLite invalidation | Migration restores account restriction invalidation and maintains exact public/artificial/disabled projections. Worker PB finalization and moderation share a player lock so concurrent restrictions cannot corrupt cached populations. |

Migrate a backed-up database to `0014_storage_lifecycle` and rebuild API/worker together before rollout. Migrations backfill current PBs, distinct finishers and active queue counts on both PostgreSQL and SQLite. They deliberately require a matching backup for downgrade because archived optional evidence cannot be reconstructed. No migration was applied to existing services by this task.

## Measured load

Windows/WSL loopback laboratory, 8 concurrent clients unless specified. Data is explicitly synthetic. The first three profiles use one API with pool 4, no workers, and strict 200 ms endpoint p95 gates. Short runs include host/background variability; original Windows measurements have approximately 16 ms clock granularity. Future tool runs use the high-resolution performance clock.

| Profile | Requests / completed RPS | Largest endpoint p95 | API peak RSS | Result |
| --- | --- | --- | --- | --- |
| 1,000 players / 100 versions | 1,329 / 88.2 | 156 ms | 104.3 MiB | No errors; strict gate passed |
| 10,000 players / 1,000 versions | 1,209 / 79.9 | 172 ms | 104.5 MiB | No errors; strict gate passed |
| 100,000 players / 1,000 versions | 1,169 / 77.5 | 188 ms | 104.9 MiB | No errors; strict gate passed |
| 10,000 identical-time PBs | 932 / 77.2 | Around 203 ms | 105.6 MiB | No errors; strict 200 ms gate failed |
| Two APIs plus representative ghosts | 1,129 / 93.5 | Ghost 218 ms; around 203 ms | 107.3 / 105.3 MiB | No errors; explicit per-kind preset passed |
| Monday, 150 actors joining | 326 / 26.7 | First 538 ms; repeat 335 ms | 106.6 MiB | No errors; explicit per-kind preset passed |
| Two canonical workers, 20 requests/s | 300 / 20.0 | Upload 172 ms | 106.7 MiB | All 15 submitted attempts verified; queue drained; oldest age 4 s |
| Overload, 96 clients / 200 offered requests/s | 444 / 71.2 | Up to 3.2 s | 107.7 MiB | 46 HTTP 503s and generator drops; gate failed; subsequent read recovered in 15 ms |

These are registered population, not 100,000 simultaneous drivers. The near-flat API memory/read costs support the new projections; they do not establish production capacity. Standard fixture replay uploads in native app tests measure approximately **6.5–6.8 KB compressed**, retaining all 12,757 canonical ticks and rewind/launch channels. Conditional snapshots have zero response body on 304. Full response, pool, SQL-plan and worker memory evidence is retained alongside the checkpoint.

Two canonical workers used approximately 98 MiB Python plus 124–125 MiB engine working set each in the controlled run. Worker sizing must use measured service time and arrivals on the target host; use `workers >= arrival_rate * service_seconds / target_utilization` as a planning calculation. More API replicas cannot compensate for insufficient verification capacity. Pool maxima plus migration/backup/admin connections must remain below PostgreSQL's 40-connection configuration. CPU and memory must also fit the NAS; no DS925+ capacity is claimed.
