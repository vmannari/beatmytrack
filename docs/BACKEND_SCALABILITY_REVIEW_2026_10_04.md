# Backend/API scalability review — 2026-10-04

The backend has useful reliability boundaries, but the current deployment and request patterns are not ready for a large player population. The main constraints are verification CPU, work performed under shared database locks, global queries in rivalry matching, repeated metadata traffic, and indefinitely retained competition evidence. Small response limits alone do not bound the work required to produce those responses.

This is a review of the current working tree, including the uncommitted rivalry/test-driver/client changes. Requirements: B01–B07, B19–B20, B23, WR03–WR08, RW05–RW07 and Q01. No runtime source, simulation, schema, API contract, deployed data or service was changed. Recommendations below are proposed follow-up work; no production capacity or phone fluency acceptance is claimed.

**Evidence and scope**

The [isolated probe](evidence/backend-scalability-review-2026-10-04/review_probe.py) and [measurements](evidence/backend-scalability-review-2026-10-04/measurements.json) use disposable SQLite fixtures, synthetic players and the exact Windows engine. They do not contact the live PC backend. Canonical timing uses the existing 12,757-tick, five-lap oval and verifies the expected time on three runs. SQLite query counts describe application work, not PostgreSQL query plans or concurrency. Compression sizes are local estimates; compressed uploads are currently rejected, and the application does not configure response compression. A deployed reverse proxy might compress responses, but that was not verified.

**Prioritized findings**

1. **P1 — Production rivalry verification cannot write its ghosts.** `backend/deploy/compose.yaml:105` mounts the worker object volume read-only; `backend/bmt_backend/worker.py:159` calls `put_json()` during rivalry finalization. The PC Compose volume is writable, which masks this difference in local rollout. Injecting the expected filesystem `EROFS` into a disposable job reproduced an uncaught exception: the run remains `verifying`, with one attempt consumed. `worker.main()` does not catch this finalization failure, so the process exits; container restart and lease expiry repeat the problem and ultimately exhaust attempts. Give the worker narrowly scoped object-write access and handle storage/database finalization failures with durable bounded recovery. Verify the actual production Compose permissions with a rivalry upload, ghost retrieval and worker restart test before release. This is a confirmed configuration/code mismatch; the probe simulates EROFS rather than deploying production containers.

2. **P1 — Verification capacity is far below a large active population.** Compose starts one sequential verifier worker, limited to one CPU; every competitive submission starts a fresh headless process, compiles the track and records a positional ghost, including normal runs whose ghosts are not stored. The queue cap of 128 and per-player cap of eight bound backlog, not throughput. Approximate sizing is `workers >= concurrent_racers × mean_verify_seconds / (mean_race_interval_seconds × utilization_target)`. With 1,000 active racers completing one race every 120 seconds and the desktop 2.571–3.051-second sample medians, about 31–37 workers would be required at 70% utilization; this is illustrative sizing, not a NAS capacity claim. First measure Linux/NAS verification across small, large and hazard/bridge-heavy tracks, then reduce unnecessary ghost generation and repeated compilation/startup work. Keep full canonical verification for all competitive submissions. A reusable verifier process/cache must prove complete reset, determinism, bounded memory and crash isolation before replacing the current fresh-process boundary. Scale worker replicas separately from HTTP replicas and preserve visible asynchronous result status.

3. **P1 — Global queue admission holds a shared lock during object storage.** `queueing.py:10`, `runs.py:225–235` and `tracks.py:223–236` hold the same `operation_state['queue']` lock through JSON encoding, immutable-object publication, fsync, inserts and idempotency commit. Worker claims also acquire that row (`worker.py:57`, `track_validation.py:16`). A slow upload publication stalls unrelated submissions and worker claims across every replica. `SKIP LOCKED` on job rows cannot remove contention on the separately locked shared row. Move durable object preparation outside this shared critical section, then perform a short atomic capacity reservation and job commit; preserve idempotency and safe collection of abandoned objects. Use bounded queue counters/reservations or partitioned admission rather than repeated counts under a global lock. PostgreSQL holds these locks until transaction end; this contention analysis is inferred from code and [PostgreSQL's locking rules](https://www.postgresql.org/docs/17/explicit-locking.html), not a measured contention run.

4. **P1 — Rivalry discovery/matching performs work proportional to global history.** `rivalry.py:70–118` computes distinct finishers over PBs across versions, computes latest versions, random-orders eligible candidates and loads full version rows before filtering compatibility in Python. The 1,000-row limit occurs after aggregation/random selection and before compatibility filtering; it neither bounds query work nor ensures all compatible candidates are considered. Unjoined `/rivalry/current` invokes this query just to report eligibility. `skill_score()` issues up to 61 statements for 20 historical boards: one selection and three counts per board. It also lacks an index led by player/recent achievement time. Monday joins can concentrate these costs; creation of a group performs eligibility work while holding the cohort matchmaking lock (`rivalry.py:252`). Maintain eligibility projections per version and contract, precompute bounded player skill summaries, put compatibility predicates into indexed columns, and sample IDs from an eligible set. Keep projections synchronized with bans, official provenance, ratings and distinct verified finishers. Reduce three per-board counts to one aggregate as an interim repair, and move expensive selection outside capacity-reservation locks.

5. **P2 — Reads lock rivalry writers, while the response repeats stable data.** `rivalry.py:170–192` takes `FOR UPDATE` on the group for every snapshot and then reads standings, all pending history and five version/track/owner records. Reads within a group serialize and can delay verification and joins. Five-track/twenty-player Python scoring is itself well bounded; the avoidable costs are locking, query round trips and repeated representation. Use a coherent read-only snapshot or a revisioned projection, batch metadata joins, and release database resources before response encoding. Return stable track/driver metadata once and a compact score/status revision for refreshes. A group revision must cover membership, PBs, bans and availability. At 10,000 users viewing rivalry, 30-second refreshes of this sample imply roughly 333 requests/second and 11.84 MB/second of uncompressed bodies (about 95 Mbps), even if nothing changes. This workload is a scenario calculation, not live usage.

6. **P2 — Compression, conditional reads and coordinated polling are incomplete.** `middleware.py:175` rejects compressed requests; `app.py` has no compression middleware, and most reads get `no-store`. Public track documents already implement ETags correctly, so preserve that visibility check. Lossless compression cut the representative replay from 147 KB to 6 KB and weekly snapshot from 35.5 KB to 6.1 KB. Add response compression at the configured edge/application and a bounded, versioned compressed or binary input-upload format with strict expanded-byte/frame/node limits. Preserve the full quantized 120 Hz sequence, launch marker and rewind receipts. Consolidate the outbox/run-result and rivalry-result reads, honor a server-suggested delay, jitter retries and polls, and slow down while a queue is congested. Existing single-flight result polling, backoff and durable retry keys are valuable; extend them rather than introducing mandatory continuous WebSockets. Discovery should fetch the visible page, retain cursors/filter scope and request more on demand instead of three 100-entry pages on a routine refresh. Existing server search can be reused.

7. **P2 — Popular leaderboards still require population-sized scans.** `runs.py:293–437` uses indexed PB ordering, bounded pages and coherent leaderboard transactions, but cursor positions, around-me ranks and percentiles issue exact count-range queries. Histograms scan board entries twice on cache misses. `board_cache.py` retains only 128 process-local results; every PB update increments `stats_revision`, making previous aggregates unusable, and concurrent misses are not coalesced. Hot boards can therefore continually recompute scans; replicas do not share the cache. Keyset pagination bounds returned rows, not the count work done to number them. Keep exact canonical PBs and tie semantics, but maintain/cache aggregate statistics and rank projections with an explicit freshness policy. Coalesce cache misses, combine related result queries and add a player-led recent-PB index where plans justify it. Exact PostgreSQL counts require scanning qualifying index/table entries; see the [aggregate-function documentation](https://www.postgresql.org/docs/17/functions-aggregate.html). Verify `EXPLAIN (ANALYZE, BUFFERS)` on realistically populated boards before choosing further indexes or a ranking store.

8. **P2 — Valid large uploads can exceed aggregate memory budgets and cause phone stalls.** The parsing semaphore in `middleware.py:93` limits two simultaneous decodes, then releases before the handler has finished using the tree. At twenty-four such in-flight requests, the measured retained trees plus original body buffers alone would occupy approximately 712 MiB, exceeding the API's 640 MiB budget before other allocations; this is an allocation-envelope calculation, not an observed OOM. Untrusted bodies are also completely buffered before parsing. On the client, `backend_client.gd:216–247` and `379–406` create a new HTTPRequest for each call, copy/normalize all replay frames, stringify request bodies and parse response JSON on the main thread; outbox integrity checks and saves perform additional encoding/I/O there. Awaiting network completion does not make this CPU work asynchronous. Introduce a separate admission/memory budget for large-body lifetimes, smaller endpoint-specific bounds for ordinary requests, and background/bounded replay serialization and cache writes. Measure frame time during upload/retry/ghost download on a real phone. Godot supports threaded HTTP transport and gzip reception, but changing transport alone does not move surrounding GDScript JSON work off the main thread; see [HTTPRequest documentation](https://docs.godotengine.org/en/stable/classes/class_httprequest.html).

9. **P2 — Optional ghosts can delay race start by a full request timeout.** `_start_rivalry_race()` awaits `_rivalry_ghost()` before starting the race (`game/core/app.gd:1087–1096`); the adapter permits a 30-second request timeout and does not persist/cache ghosts. Restart repeats the fetch (`app.gd:2309`). A slow ghost endpoint holds the loading screen even when the track is cached and the ticket has been issued. Cache by immutable run ID with an LRU/byte limit, prefetch the selected rival, fetch independent resources concurrently where possible, and give optional ghosts a short deadline/fallback. Visibility/auth checks must remain server-authoritative; do not make stale shared ghosts bypass account restrictions.

10. **P2 — Long-term retained data and shared storage constrain migration.** `maintenance.py:34–44` correctly protects PBs and weekly bests, but all historical `RivalryBest` runs and every `RivalryTicket` are retained indefinitely; groups, memberships and embedded track previews have no archival lifecycle. Idempotency records are tombstoned rather than expired, and all immutable track revisions remain referenced. For an illustrative 10,000 daily racers × 20 races, the four-channel sample alone is 29.4 GB/day before compression, replicas or backups. Five weekly bests for 10,000 entrants retain roughly 15.1 GB/week of input+ghost objects at the measured sample sizes, about 0.79 TB/year, assuming one vehicle/field and all five tracks completed. Actual workloads may differ substantially. Define separate retry, non-PB, weekly evidence, historical-score and private-revision retention policies; historical score summaries need not retain every pose/input blob forever. Never expire permanent resume-grant identities or enable duplicate fulfillment by blindly deleting idempotency keys. The current destructive GC requires stopping every writer, and backup stops API/worker too. Both become availability limits as data grows. A cloud object adapter and tested consistent online backup/GC strategy are needed before multi-host scaling; `BlobStore` is a useful starting seam, but the implementation requires local paths, fsync and hard links, and operations/GC directly inspect that filesystem.

11. **P2 — HTTP replicas require a deliberate database and abuse budget.** The API engine allows up to ten connections per process (`db.py:28–30`); production PostgreSQL allows forty total connections (`compose.yaml:51`). Adding API processes without reserving capacity for workers/migrations/administration can exhaust that pool. The default SQLAlchemy pool wait can consume much of the client's 30-second deadline. Make connection/pool deadlines and per-role limits configurable and test aggregate saturation. Read limiting is shared and reserves ten-request leases, which is a good safety property, but its 600/minute budget is keyed only by IP (`middleware.py:147–163`). Carrier NAT or a large shared network can throttle unrelated legitimate players; writes/auth can contend similarly. Preserve edge/IP protection and use authenticated player/session plus weighted expensive-operation budgets, with separate controls for public discovery and uploads. Rate-limit reservations themselves perform database writes, so include them in load tests rather than measuring handlers alone. The track API also retains a synchronous validation path when `defer_validation` is false (`tracks.py:113–138`, `170–172`): this starts Godot in the HTTP process while its session has already queried authentication/idempotency data, bypassing durable queue admission. Make deferred validation the enforced public path, or give any retained operator-only synchronous path a separate strict budget.

12. **P2 for local/test correctness — SQLite migrations drop restriction cache invalidation.** After migration to 0012, the disposable database has only the three `pb_revision_*` triggers; `player_board_revision` is missing. The players-table rebuild in 0012 does not restore the 0008 trigger. The existing `test_board_cache_tracks_pbs_and_restrictions_across_sessions[sqlite]` reproduces population 3 after disabling Bob, where 2 is expected. This can leave count/histogram responses inconsistent with filtered rows in SQLite test instances. Production requires PostgreSQL and its ALTER-table path differs, so this is not evidence of the same production defect. Restore the SQLite trigger and require the regression to pass; separately verify PostgreSQL invalidation and account/test-population changes under concurrency.

**Architecture that should be preserved**

The modular monolith and PostgreSQL are reasonable for this product; a microservice rewrite is not required by these findings. Identity, immutable content, competition and fulfillment are separated; credentials are hashed, development identities are gated, grants/writes are idempotent, inputs are quantized, contracts are pinned and verification is server-authoritative. Leases fence stale workers, expensive simulation usually runs outside transactions, input/body deadlines are bounded, raw rival controls are not shared publicly, downloaded tracks are hash-checked and cached, and normal race results do not wait for backend verification. These reduce failure propagation. Improve the shared-lock boundaries and data projections before splitting services.

A practical deployment progression is independently replicated stateless HTTP adapters, a measured verifier pool, PostgreSQL with explicit connection/query budgets, and an immutable shared-object adapter. Keep cached/read projections bounded and revisioned, with hard domain writes in PostgreSQL. An additional caching service is an option after measurements justify it, not a requirement for the first repairs. Offline local racing and canonical simulation must remain independent of all these changes.

**Proposed acceptance work**

Agree expected concurrent racers, browsing users, race interval, traffic budget and latency targets before setting capacity. Suggested initial engineering targets are ordinary metadata API p95 below 200 ms excluding network RTT, bounded verification queue age, and no serialization/upload-induced violation of the phone's frame budget; these are proposals, not owner-approved SLAs. Track bytes/request and bytes/player-session alongside p50/p95/p99, DB pool/lock waits, query rows scanned, RSS, verification seconds/track, admission failures, oldest job age and client frame time. Existing structured logs omit body/response byte counts and worker timing, so current instrumentation cannot enforce a traffic budget.

Use representative distributions rather than one huge uniform fixture: 1K/10K/100K players; popular boards with 1K/10K/100K PBs; thousands of versions; carrier-NAT cohorts; Monday membership bursts; reconnecting outboxes; complex tracks; three rewinds; and a multi-day soak with retention/backups. Run cold/warm caches and multiple API/verifier replicas. Exercise disk-full/read-only errors, worker death after object publication, duplicate retries, DB outages, rate limiting and session refresh under packet loss. Prove no duplicate grants, no unverified rankings and no loss of saved attempts. Benchmark PostgreSQL plans/contention and the actual NAS CPU/disk before extrapolating the Windows sample. Capture physical-phone frame/network traces during race start, uploads, weak-network retries and ghost loads.
