# Cold loading and shader preparation — 31 October 2026

This pass removes some repeated preparation work, but **does not fix the multi-second first-use Compatibility driver stall**. It does not establish a phone speedup or a 60 FPS loading guarantee. The earlier [native shader investigation](NATIVE_SHADER_PREPARATION_2026_10_28.md) and [follow-up](COLD_SHADER_FOLLOWUP_2026_10_30.md) remain relevant: synchronous GL compilation/linking was measured inside a large first-use frame, and the separate compiler prototype did not meet its first-draw and memory gates. Switching renderer or shipping an unsupported executable hook is not justified by that evidence.

## Current actual-App observation

Two sequential fresh private application profiles on Windows Compatibility, Godot 4.7.2 and an RTX 3090 each ran the actual App's Star fixture twice. The first profile observed **76,247.498 ms** to first race with a **10,356.835 ms** largest frame, then **2,871.849 ms** with a **301.107 ms** peak on repeat. The final-source profile observed **58,125.582 ms** and **7,143.539 ms**, then **3,144.001 ms** and **262.803 ms**. Each process passed its ten state, pause and readiness checks. Other processes were active, source edits occurred while the first process ran, and the driver's global caches were not cleared; these are **not a controlled before/after comparison**. Neither run instrumented native driver calls. They confirm that a severe current desktop stall remains but cannot attribute either particular frame to shader compilation or predict an Android result. The sandbox emitted a Windows certificate-store error. The [timing rows and redirected workload](evidence/cold-loading-followup-2026-10-31/) are retained; screenshots and private profiles are under `build/cold-loading-20261031/`. The workload is derived from `game/tests/profile_runtime_correctness.gd` with its output redirected and `--only-star`.

## Repeated work removed

- Particle emitters now share equivalent immutable shader resources while retaining independent material instances, uniforms, particle processes and meshes. Weak references ensure the new lookup does not extend a shader's lifetime beyond its existing live or prepared-template owners. A Winter fixture reduced 12 shader object identities to five, corresponding to five distinct code strings; 32 materials remain distinct. This does **not** reduce the number of staged particle draws, and resource identity is not itself proof of fewer native driver compilations.
- Winter environments reuse one unchanged, static reflection sky. The existing memory-pressure and retained-budget path can release the optional cached reference without altering a currently active environment. The 1 MiB accounting entry is an estimate, not a measured GPU allocation.

An interleaved headless Winter emitter-construction microbenchmark measured median **54.224 ms before and 25.571 ms after** after warmups while clearing emitter templates. An earlier run under concurrent activity measured 81.8 and 38.2 ms, illustrating variability. This is a component result, not full-race loading or Android timing. A separate Compatibility reflective-sphere test alternated new and reused Winter sky resources: median first post-assignment interval was **5.223 ms versus 0.380 ms**, with 24/24 settled images byte-identical. The test's GPU timing is asynchronous. A previous run reported two texture leak warnings at shutdown; after correcting the fixture's cleanup loop, the repeat exited without those warnings. The actual Winter scene regression also exited cleanly. Neither experiment establishes a fix for the first driver compile. The [sky evidence](evidence/winter-sky-reuse-2026-10-31/README.md) describes the controls and test limitations.

A bounded joined-road contour cache was also tested and reverted. Although one component sample improved, two alternating 96-piece cold planning runs were **3,994/3,311 ms before versus 4,098/3,928 ms after**, with identical packet hashes. The cache added about 530 KiB of sampled retained static memory. Those observations do not justify shipping it as a loading improvement.

## Validation

The current particle implementation matches an in-memory immediate task-start reconstruction across five themes and bridge/no-bridge cases: **139 headless and 462 Compatibility assertions, zero failures**. The Compatibility comparison emitted shader-cache write and certificate-store errors in the sandbox, so it is not a clean run. The actual-App Compatibility subset completed **23 checks, zero failures**, covering a Winter race, first emission, cancellation and pressure. Its first race took 53.068 s; without a matched pre-change run this is not a speedup measurement. The new shader identity, material independence and weak-release regression exits zero; its initial version failed because a test-local material reference kept a shader alive, and passed after correcting that fixture.

The headless Winter sky lifetime and App pressure regression passed **13/0**. The graphical Winter scene passed **109/0**, including reflection and seam coverage with zero unstable restored pixels. The exportable-source parser passed **504 scripts**. Offline Windows runs reported certificate-store errors. A desktop Mobile/Vulkan actual-App first-emission test timed out after 180 seconds with no result; the test process was stopped. Renderer startup and certificate/access errors were observed, and this is not a pass. No Android device was tested.

## Remaining work

The largest available desktop attribution identifies individual blocking driver link calls. A script-level frame budget cannot interrupt one of those calls. The existing background compiler experiment imported binaries but left **221–235 ms** first-draw frames and exceeded the **96 MiB** optional-work memory budget on its measured desktop case. Further work must establish a supported, bounded engine/driver path, test first real draws and failure/pressure/context-loss recovery, then validate on representative Android devices. Until those gates pass, retain the existing covered preparation and visual features.
