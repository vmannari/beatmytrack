# Backend communication L1–L3 — 2026-10-13

Review IDs L1–L3; project requirements B01, B05, B07, Q01. Source fixes and regression evidence; no production deployment, live account/data writes or canonical simulation changes.

## Result

| Item | Change |
| --- | --- |
| L1 | Complete the existing HTTP-date Retry-After support: preserve numeric zero, handle century rollover and the exact RFC fifty-year boundary. Retain all three HTTP date forms, server-date/clock references, malformed-date rejection and the existing one-hour bound. |
| L2 | Retain the existing validated UUIDv4 header capture; preserve correlation when a response fails schema validation and decode malformed JSON without emitting an engine error. Backend request logs resolve declared route templates for failures rejected before routing, including nested/prefixed routers and wrong-method matches. Private path values, query strings, bodies and credentials remain absent from the log. |
| L3 | Pin the official Python 3.12.15 Bookworm image by digest, add SHA256 hashes for every locked package, enforce hash checks and wheel-only installation, pin the existing setuptools builder, and build the local project with dependency/build isolation downloads disabled. |

L1 date parsing and the first part of L2 header capture were already present at task start. Their existing behavior and concurrent telemetry work were retained; the remaining defects were fixed and exercised over actual HTTP. The date-window behavior follows [RFC 9110 HTTP dates](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.6.7). Hash enforcement and source-distribution exclusion follow the [pip secure-install guidance](https://pip.pypa.io/en/stable/topics/secure-installs/); immutable base selection follows [Docker's guidance](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions).

The base is `python:3.12.15-slim-bookworm@sha256:34386ef0cb081344d7ec1c103ba398e6e9f64e9ab3a1509accc92a4e24a07258`. The digest was read from the official registry and independently checked against the manifest bytes. `setuptools==84.0.0` is pinned in both the build contract and the hash lock. The lock contains 46 packages and 992 published wheel alternatives; all previous application package versions, including patched cryptography 50.0.2, are retained. The FastAPI minimum is aligned with the effective-route API actually used and tested (`>=0.141`). The unpinned external Dockerfile frontend directive was removed; the installed builder supplies the standard frontend.

The lock refresh helper only reads explicitly selected versions from official PyPI metadata, refuses ambiguous/unpinned entries, excludes yanked artifacts and source distributions, and publishes the new lock only after every package has valid hashes. Its receipt records each artifact/source. Hashes freeze the reviewed artifact bytes; the refresh itself remains a reviewed dependency change.

Initial tracing tests exposed the framework's included-router wrapper behavior; simple top-level matching could not recover the prefixed template. The implementation now uses effective route contexts, and the original assertions remain. The first wire fixture used a UUIDv1 despite the existing telemetry contract requiring UUIDv4; the corrected fixture uses the server's actual format. Malformed JSON also exposed the noisy decoder and is now handled quietly. An initial mixed local test run picked up an unavailable pre-existing PostgreSQL port; final checks use a separately created owned database instead. These initial runs are not counted as passes.

## Scope and remaining acceptance

The full verifier/OS-library stage was not rebuilt or deployed for this change. Debian's signed package repositories remain updateable, so the complete image is not claimed to be byte-identical across future OS-package updates. Pinning the base and Python artifacts requires deliberate security refreshes. No full Validate, physics/replay suite, Android export/install or physical-device test was performed; canonical code and visual layout are unchanged.

Production still uses its existing image. Backend rollout and restarting/updating game clients remain separately authorized acceptance steps. During rollout, check a real date-based retry and trace an early failure through its client request ID to the safe backend route log.
