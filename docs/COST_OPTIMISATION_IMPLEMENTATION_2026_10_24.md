# Download and operating cost implementation

The local implementation now reduces repeated downloads, object-store operations, hot receipt rows, repeated CPU work and request-log volume. Google Cloud remains sufficient for these changes. The 95% cost reduction remains a target requiring measured traffic and bills; it is not a demonstrated result.

This implements the recommendations in [Download and cost optimisation](DOWNLOAD_AND_COST_OPTIMISATION_2026_10_24.md), following the corrected [performance review](BACKEND_PERFORMANCE_REVIEW_2026_10_24.md) and [Google-only scenarios](GOOGLE_ONLY_COST_OPTIONS_2026_10_24.md). Per-race acceptance remains the existing Python trajectory checker. No native replay was added to ordinary race acceptance.

## Download protocol and budgets

Bootstrap advertises `ghost_identity_version=1`, `ghost_wire_version=1` and `discovery_preview_version=1`. Existing clients receive ordinary JSON. New clients can request `metadata=true` on the existing recording routes; this resolves the currently permitted source without fetching its object. A missing disk entry then requests the body with `expected_run_id` and optionally `encoding=packed`. A changed source returns409. Conditional replies are private, require revalidation and happen after current access checks.

`bmt-packed-ghost-v1` contains base64 gzip of little-endian seven-Float64 rows. It retains every numeric sample and duration; it does not alter score/proof formats, sample rate or interpolation. The server selects it only when actual compressed transfer is at least5% smaller. The saved2,130-sample projected path fixture falls from63,487 to47,400 compressed bytes, **25.34%**, with exact numeric round trips through Python and the native client. This fixture has zero banking and is not a population download measurement or device CPU benchmark.

Recording disk usage is bounded at64MiB/64files, with8MiB encoded/decoded per entry and at most16 shared in-flight recording preparations. The ordinary GET coalescer allows64 distinct pending reads. The server representation cache holds at most32MiB/256entries and permits four preparations at a time. Existing track-document caches, gzip policy, batched completion waits, retry backoff and accepted two-viewport discovery preload remain.

Rivalry retains its existing 30-second RAM freshness cadence. After that interval, current metadata gates persistent reuse of unchanged bytes instead of forcing another recording download. Explicit account and community-block changes still fence late responses.

The preview request permits at most32 retained preview hashes. Missing/corrupt local previews trigger a full response without hints. Full route points remain the default for clients that have not negotiated reuse. The discovery and packed-recording JSON schemas were updated.

## Storage and SQL lifecycle

Defaults leave new packing and automated cold archival disabled. The explicit cost profile enables packing, a seven-day hot retention interval and seven-day receipt archival. Packs contain at most128records and6MiB, with a five-second partial flush policy. Intake admits at most64MiB and8,192pending records per partition before retryable backpressure. Acknowledgement follows durable SQL commit; pending bytes are authoritative until a verified pack upload and atomic location switch complete. Oversized records retain individual-object storage.

Packed records retain their original canonical content SHA256. Reads request the individual compressed frame and verify its logical hash. Upload intent/hold leases prevent collection between upload and location publication. Packs with at least50% dead bytes can compact after ten minutes; retired pack readers receive a grace interval of at least ten minutes. Backup guards pause retirement/compaction. New-object garbage collection uses indexed candidates, references and pins; legacy cleanup keeps a bounded periodic scan.

Retry archives preserve original identity, request hash and exact response rather than probabilistic deduplication. Existing90-day v2-key expiry stays authoritative; chunks expire only beyond100days. Legacy keys stay protected. Missing keys, damaged archives or excessive overlapping candidates fail closed. Archives use the already-installed AES-GCM dependency, per-account keys and identity-bound authentication. Account erasure removes those keys. Backups still require the existing privacy-aware restore process; restoring old keys without replaying erasure records is not permitted.

Reward archives retain original per-run receipt detail and financial entry detail. Run metadata prevents duplicate credit. Hot earned ledger rows are folded into exact anonymous per-second amount/count totals, preserving arbitrary integer timestamp finance windows. Wallets, purchases, entitlements, competitive PBs, creator evidence and protected active history retain their existing rules. Seven days is a storage-tier boundary, not a change to purchase/reward promises.

Packing adds SQL writes, WAL, indexes and recovery work. At large traffic this may shift cost to PostgreSQL IOPS/CPU. Index growth, backup duration, archive lookup overlap, partial-pack occupancy and foreground p95 need production-shaped PostgreSQL calibration before enablement. Defaults are conservative local bounds, not a certified one-million-player hardware allocation.

## Google-only operating choices

Generate a proposal with `python backend/deploy/gcp/cost_profile.py --api-service <owned-service> --output <review-file>`. The retained example uses the illustrative name `bmt-api`; no cloud policy was applied. The profile proposes sampling only successful Cloud Run request logs, retaining application aggregates/errors/slow requests and financial/security audits. Application compressed-body counters exclude headers/TLS; reconcile them with provider totals for billing.

Keep request billing at quiet traffic and compare instance billing under sustained measured traffic. The configuration exposes that choice explicitly. The packing worker receives its own one-connection allowance, low Linux priority and bounded maintenance turns; it yields expensive work during verification backlog or backups while intake continues draining. The staging profile reserves1GiB worker memory when packing is enabled; this is an allocation, not measured RSS.

Co-locate database, bucket and compute, then choose any additional region from measured latency. CDN delivery is not free bandwidth and can add cost after local reuse has removed repeats. No managed cache is required by this implementation. Mixed live/history buckets must not receive a blanket age-delete rule. Inspect soft-delete/version copies and backup protection before changing provider retention. Commitments wait for a sustained baseline; Spot remains suitable only for separately checkpointed offline work. Active development resources and artificial-driver behaviour were preserved. No purchase, resource deletion or provider mutation was performed.

## Rollout and remaining acceptance

Before enabling the cost profile: migrate0065/0066 with the matching current migration chain, apply explicit workload grants, deploy compatible readers/API and supervised worker together, rehearse a complete database-plus-object restore, then calibrate PostgreSQL concurrency and workload cost. Existing-table archive indexes use PostgreSQL concurrent creation with failed-index retry handling. Old binaries cannot safely read the new schemas; downgrades refuse to discard authoritative packed/archive data. Disabling new writes is the tested reversible configuration path while retaining the compatible reader.

Measure returning/new-player p50/p95 bytes, week-start/cache-miss bursts, endpoint calls, pack fill/operation counts, SQL WAL/IOPS/CPU/index growth, archive recovery, restore duration and foreground p95. Compare provider invoices to the corrected model;0.2MiB/player/day and a95% bill reduction remain targets. Revisit commitments or hardware only from that evidence.
