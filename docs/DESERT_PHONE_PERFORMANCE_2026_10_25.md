# Desert phone performance, 2026-10-25

DPP01–DPP03 / R01 / G01 / V05 / Q01. The owner reports poor Desert performance on the installed OnePlus DN2103. The final optimized build is installed, its APK hash/version verified, and normal play restored with app data retained.

The same installed-source Compact/Desert diagnostic route reproduces about **43.1–43.8 FPS**. Three original full-scene windows have frame medians **22.509–22.887 ms**, p95 **32.959–33.432 ms**, and p99 **40.453–42.054 ms**. Vehicle dust off and flat terrain/road controls remain around the same speed. The legacy `half_scale` control equals the already-selected 0.5 render scale and is not evidence of a resolution comparison.

Two changes address CPU work:

- `desert_sand_wind.gd` retains only the same nine local artwork tiles. Static road/bridge/relief/source-support results are reused; configure invalidates them. Source order, roots, heights, site retention and the 96-quad pool remain exact. Moving-route support queries fall to 12.6–12.7% of the original. A 720-call desktop lookup benchmark changes median/p95 from 2495/4278 µs to 20/1058 µs. This initially reduces scan spikes, but a phone cache-only build still runs about 43.3–44.5 FPS; it does not solve the sustained slowdown alone.
- `desert_ambience.gd` uses `desert_playback_clock.gd` to follow the actual mixed playback position plus monotonic presentation time, avoiding a driver timing query every frame. Random offsets, loop wraps, output-latency correction, pause/background/retry and existing audio/gust gains remain. Prediction is capped at 50 ms; sparse out-of-window phone reference checks differ by 14.89–37.39 ms, below one 20 Hz envelope sample. This is sampled synchronization evidence, not a claim of sample-exact audio phase. Native recorded wind/sand coupling passes through an actual loop wrap.

Godot's public [audio-driver implementation](https://github.com/godotengine/godot/blob/master/servers/audio/audio_driver.cpp) shows the timing getter taking the driver lock. That source informed the investigation; the phone measurements establish this task's effect. The final diagnostic reference query itself takes up to 12.133 ms outside measured windows, while regular weather presentation drops from roughly 3.9–4.3 ms to roughly 0.13 ms at the median.

The two final 25-second full-scene phone windows measure **59.41/59.39 FPS**, median **16.484/16.552 ms**, p95 **20.969/20.990 ms**, and p99 **23.048/22.726 ms**. A further 60-second moving run covers **533.14 m**, with zero paused frames, median **16.527 ms**, p95 **20.809 ms**, p99 **23.094 ms** and maximum **39.803 ms**. Android SurfaceFlinger independently records **2784 presented intervals over 46.908 seconds** (59.35 FPS), median **16.836 ms**, p95 **16.990 ms**, p99 **17.086 ms**, and two intervals over 25 ms. These are different measurement boundaries; the engine callback p95 still exceeds 20 ms. No hitch-free or long thermal-session certification is claimed.

All comparisons use the existing Compatibility renderer/Mali-G77, 2400×1080 window, 0.5 world scale and 2× MSAA. Camera, lighting, textures, native libraries, particle/site population, canonical physics and scoring are unchanged. The final APK audit confirms 2910 packaged artwork/audio/native entries identical to the original installed APK. It adds the clock script and changes only Desert source discovery, Desert audio timing, the local debug probe and generated build identity.

Validation: cache 34 headless / 51 Compatibility / 51 desktop Mobile checks; original wind lifecycle 168; ambience 125; clock 23; isolated synchronization 44 headless / 56 Compatibility (181 recorded frames, one wrap, linked=true); Android import/startup plus 72 driving / 21 catalogue / 41 menu checks pass. A concurrent root font-fallback typed-array error stopped one synchronization run; the exact isolated phone sources pass. Initial locked-phone profiling yielded zero stages and was cleaned up; it is not included in performance results.
