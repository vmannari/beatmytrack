# Download and operating cost optimisation

**Prioritise reuse of downloaded ghosts, smaller menu refreshes, packed object writes and bounded active SQL. Keep the current Google stack while measuring their effect.** The earlier 0.2-MiB/day/player download budget is a target, not observed demand. Ten different recordings or a large catalogue browse can exceed it even when caching works correctly.

This source audit follows the [Google-only scenarios](GOOGLE_ONLY_COST_OPTIONS_2026_10_24.md) and [cost reduction design](BACKEND_COST_REDUCTION_PLAN_2026_10_24.md). Requirements DCO01 establish existing savings, DCO02 minimise downloads without changing racing, DCO03 rank other operating savings, DCO04 evidence and preservation. No runtime, provider, billing, data-retention or deployment changes were made.

## Existing savings and concrete gaps

| Area | Current source observation | Remaining opportunity |
| --- | --- | --- |
| Track documents | Exact downloaded document persists under its content hash; a valid local hit returns before HTTP | Retain this behaviour; measure misses and evictions rather than count every race as a new track download |
| JSON transport | API gzip already covers responses at least 1,024 bytes, at level 3; compatible uploads also compress | Verify actual compressed wire sizes; do not claim gzip as a new saving |
| Conditional reads | Client sends ETags when available; track documents and Rivalry snapshots support conditional replies | Cover more suitable reads and persist bounded validators; avoid rebuilding a full snapshot just to discover its generation did not change |
| Rivalry ghosts | Cache key includes run ID; freshness expires after 30 seconds; cache is process-local and bounded | Persist immutable recording bytes by source identity rather than expire unchanged bytes after 30 seconds |
| Challenge ghosts | `ghost()` fetches the recording each call; the examined server handler supplies no ETag | Share a recording cache and fetch only after resolving the current target run/hash |
| Discovery | Twenty-row pages, manifests already omitted, up to 96 route-preview points; client keeps the accepted two-viewport reserve | Separate immutable previews from volatile counts and reuse them across queries/pages/restarts |
| Race completion | Batched status reads, bounded completion waits, server polling intervals and retry backoff already exist | Coalesce remaining duplicate consumers and send compact terminal outcomes; do not add another concurrent polling loop |
| Metrics | Client records the completed body size; server boundary records response body bytes outside gzip | Use server compressed-body counters and provider transfer totals for costing; client decoded sizes are not wire egress |

Godot's default HTTPRequest accepts gzip and returns an automatically decompressed body to the completion signal. The current client measures that body. The server's compressed-body counter still excludes response headers and provider-specific routing/accounting, so reconcile it against Google transfer metrics rather than treating either counter as the entire bill. ## Reduce downloads in this order

1. **Reuse immutable ghost recordings across races and app restarts.** Key bytes by server, recording/run identity, encoding version and applicable account/competition scope. Keep a bounded disk cache with last-used eviction and single-flight downloads shared by preview and race start. Refresh the small current-target identity separately. Check current access, withdrawal and community-safety state before reuse; clear the affected scope on account changes, blocks or source withdrawal. The current dynamic `/ghost` URL can point at a different best run, so caching that URL indefinitely would be wrong. Preserve the exact recording and current no-recording fallback.

   Illustration, not a measured recording: one 60-KiB compressed ghost fetched ten times costs 600 KiB; fetching it once costs 60 KiB. That is 90% of those repeated bytes avoided. Ten distinct ghosts still cost 600 KiB. Measure reuse before assigning a percentage to the whole game.

2. **Send compact menu cards, and download detail only when used.** A card needs its visible identity, title/creator, theme, rating and route preview. Keep full authored documents, full participant histories and recordings out of list replies. Current discovery already omits manifests and caps previews; the next step is a stable preview hash and a local preview dictionary. Separate rating/finisher updates from unchanged route points. Keep the actual locally drawn scenic preview and accepted two-viewport preload behaviour; a separate PNG download per card would add a new transfer stream.

3. **Refresh changed state rather than whole pages.** Use compact generation/version checks, ETags and bounded per-screen freshness. For changing standings, return only changed rows when a valid retained generation exists, with a full bounded snapshot fallback. Share in-flight reads among consumers. Refresh when a screen becomes visible, after an authoritative event or when freshness expires; stop optional refreshes when hidden/backgrounded. Preserve current result, source, competition and account fences. Tickets, attempts, ownership and reward decisions stay authoritative.

   A 304 response avoids the body but still creates a request and can perform SQL work. Fresh local state avoids the request altogether; an early generation check avoids expensive snapshot construction. Authenticated personalised data must remain private. The existing discovery POST contract needs an application cache keyed by query, generation and identity; it does not become safe for shared CDN caching merely by adding a header.

4. **Seed recurring official content through the install/update channel.** Consider including the exact documents/previews of the five trusted official tracks and common immutable manifests with the game. Use them only when their hash and supported compiler/rules match the server selection. Admission, moderation and tickets still come from the server. This shifts bytes into app distribution and increases install size; it does not eliminate all delivery cost. New community tracks still download on demand.

5. **Improve encoding after measuring the remaining large responses.** Gzip is already present. Benchmark a versioned, compressed binary ghost representation against the actual gzipped JSON, including decoder CPU and device memory. Prefer lossless delta/tick encoding and exact numeric reconstruction first. Preview-only coordinate encoding can be considered separately with visual acceptance; never round proof coordinates or change canonical geometry/times. Do not enable Brotli by assumption: the current Godot transport negotiates gzip/deflate, so another codec needs deliberate client support.

6. **Use CDN caching for eligible shared content.** It reduces origin reads and CPU and can offer cheaper delivery, but every cache hit still has lookup/transfer charges. Stable authorised content identities avoid unnecessary cache fragmentation. Keep private documents and recordings behind their existing access rules; do not expose whole archive packs or cache all authenticated API responses. Device reuse is the mechanism that removes repeat transfers. [Cloud CDN pricing](https://cloud.google.com/cdn/pricing), [cache behaviour](https://docs.cloud.google.com/cdn/docs/caching).

## Other operating cost reductions

| Priority | Change | Why it matters and what must remain |
| --- | --- | --- |
| Very high at scale | Pack records before the first billable object write | Two writes per race at ten million races/day means 600 million writes/month. The retrieved regional Class A rate gives about €2,639/month for those writes alone. Ideal full 128-record packs reduce that component to about €21, before durable intake, partial flushes, indexes, compaction and recovery. Packing only after individual uploads keeps the original charges. A safe durable intake must acknowledge only recoverable data. |
| Very high | Bound active SQL and indexes | Keep current PBs, active competitions, exact balances/receipts and a small recent-detail window hot. Compact older facts into searchable archives; avoid indefinitely accumulating the current 90-day ordinary detail at target population. Protected source runs and reward/purchase retry correctness remain. Smaller tables also reduce index work, WAL, vacuum, backups and restore time. |
| High | Reduce unnecessary SQL mutations | Update PB/order projections when a result improves them; coalesce dirty-board invalidations and low-priority projections. Every accepted race still receives its earned base rewards and durable once-only result. Avoid rebuilding the same board/ranking aggregate on every read. Current bounded workers and incremental mechanisms must be retained and measured. |
| High | Right-size API/worker resources and connection budgets | Load-test CPU, memory, complete I/O and per-instance concurrency together. Size the sum of API, worker, reporting and rollout-overlap database pools. Higher concurrency can reduce instance count only while database waits, memory and p95 remain acceptable. Keep foreground and background lanes separate. Compare request/instance billing under real demand. |
| Medium to high | Aggregate routine success logs and optional analytics | RequestBoundary currently emits one INFO record per request. Keep cheap all-request counters/histograms and failures, sample routine success detail and avoid duplicate access logs. Do not sample financial/reward/security evidence that must be retained. Optional analytics already batch and have bounded retention; improve aggregation/sample selection where useful instead of storing every incidental interaction indefinitely. |
| Medium | Remove repeated object decode/compress work | Cache bounded immutable, authorised payload representations on servers; reuse prepared geometry. Avoid fetching, decompressing, parsing, serialising and recompressing the same ghost for every consumer. A cache must have byte limits and must not bypass current access checks. |
| Medium | Apply object lifecycle policies by data purpose | Distinguish permanent pinned sources, compact receipts, transient intake, failed uploads and replaceable caches. Reclaim orphan data through reference-aware cleanup. Audit noncurrent versions and soft-deleted copies; deleting a live object may leave billable retained bytes. Standard storage often suits short-lived hot data better than an archive tier with minimum durations/retrieval fees. |
| Medium | Keep primary services and data colocated | Avoid cross-region SQL/object calls, unneeded replication and redundant network hops. Measure worldwide latency before adding regions. Regional failover and tested backups remain requirements; an extra serving region is a separate cost/latency decision. |
| Later | Use commitments for measured steady compute | A fully used commitment can reduce the remaining compute cost. It does not reduce object operations, transfer, storage or wasted allocation. Wait for sustained measured demand. |
| Later | Use interruptible capacity for restartable work | Consider Spot workers for offline analytics, rebuilds and regenerable content only after checkpoint/retry testing. Keep durable intake and timely result acceptance independent of interrupted capacity. |
| Immediate housekeeping | Contain development/test resources | Test drivers, load generators, preview revisions, debug logging and old artifacts need explicit lifetime/budgets. Disable artificial driving in public production; preserve the current internal test-population behaviour where it is still needed. Do not delete active work or weaken representative load tests. |

Cloud Run billing depends on traffic shape; changing billing alone is not a universal saving. [Billing documentation](https://docs.cloud.google.com/run/docs/configuring/billing-settings). Storage charges include operations, retention and transfer; Nearline/Coldline/Archive minimum durations are 30/90/365 days. Soft delete can retain temporary objects after application cleanup. [Storage pricing](https://cloud.google.com/storage/pricing), [soft-delete documentation](https://docs.cloud.google.com/storage/docs/soft-delete).

Logging illustration: at the target forty dynamic requests/day and one million daily players, one KiB of combined logs per request produces about 1,144 GiB/month. At the published USD $0.50/GiB after 50 GiB, that is about $547/month. This is not an observed log size or an EUR quote, and worker/additional logs would be separate. Shortening retention alone does not remove the initial log-storage charge; filtering/sampling before log-bucket storage matters. [Observability pricing](https://cloud.google.com/products/observability/pricing).

## Measurement and delivery sequence

First use existing compressed-body counters to rank endpoint bytes, calls, repeat content hashes and storage operations for representative returning/new players. Keep total-volume counters unsampled and bounded; use sampled detail or controlled synthetic flows for unique-content/reuse analysis, without logging private bodies or tokens. Reconcile compressed body bytes plus header overhead and actual CDN/Cloud Run/GCS routing against provider totals. Record p50/p95 player-day transfer, cold-install/week-start spikes and the mix of new versus repeated ghosts/tracks. Ads and app-store downloads belong in their own accounting; they are not automatically game-backend egress.

Implement persistent ghost reuse and request coalescing first, then smaller stable previews and generation-aware menu refresh. In parallel design the durable packed-object intake and exact receipt/archive lifecycle; these are larger backend changes with recovery tests. Re-measure before choosing binary formats, a managed cache service, extra regions, commitments or a hosting migration.

At one million DAU the prior model's reduction from five MiB to 0.2 MiB saves about €7,059/month. Going from 0.2 to 0.1 MiB saves only about €209/month under the same assumptions. This sensitivity is not a measured saving or a prediction of player usage. Once downloads are low, prioritise database, object operations and logs over sacrificing features for the last few kilobytes. Savings overlap and must not be summed across an already-optimised budget.
