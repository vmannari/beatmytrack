# Track editor T05 to T11 fixes

T05-T11/R01/Q01 covers bounded undo history, lazy gesture rollback, deferred ordinary commits, initial rendering preparation, dense geometry queries, coordinated cache retention, and exact grouped prop rendering. The T01-T04 editor retention and modular construction remain in place. Saved v5 documents, compiler identities, published tracks and canonical driving formats are unchanged.

T08 removes avoidable preparation and bounds submissions; it does **not** establish a hard frame-time bound for a cold GPU driver compilation. Physical-device acceptance remains outstanding.

## Implementation

| ID | Change | Main code |
| --- | --- | --- |
| T05 | Immutable binary fields share unchanged paint, pieces and other authoring data across undo and redo. Both ordinary stacks share an 8 MiB allowance and a forty-state maximum. Oldest states are removed when bytes exceed the allowance. Restoring a state produces independent mutable authoring values. | `game/editor/editor_history.gd`; App `_remember`, `_undo`, `_redo` |
| T06 | Selection and navigation take no document rollback copy. `_start_edit` captures the fields that the active tool can mutate, immediately before the first mutation and history signal. A second finger restores those fields and the previous history; release/cancellation retires rollback data. | Canvas `_begin`, `_start_edit`, `_rollback_navigation_edit`, `_end`, `cancel_gesture` |
| T07 | Ordinary real-library commits enqueue immutable analysis, including route derivation, validation and compact workflow presentation. One analysis worker coalesces only unstarted revisions of the same library/draft. The existing ordered atomic writer handles durability. Save, Test, Share, navigation, exit and background interruption drain required work; terminal teardown cannot start new preview work. | `game/editor/commit_queue.gd`; App `_save_draft`, `_apply_editor_commits`, `_flush_editor_writes`, `_notification` |
| T08 | Editor entry builds the actual track once, removing the preceding synthetic road/bridge fixture. Warm-up uses the editor lighting instead of adding an unused omni light. At most four material/mesh combinations are submitted in each warm-up batch. Editor road installation uses 12,288-vertex / 2 ms cooperative checks; camera navigation remains available while preparation gates editing. | EditorWorld `_prepare_editing`; `material_preparation.gd::draw`; NativeTrackVisual `_budget_install`; Canvas navigation |
| T09 | Ordered spatial queries replace complete outline scans for section-cache dependencies and complete prop-component scans for overlap planning. A disjoint-set structure replaces repeated whole-list cluster relabeling. Rounded borders use adjacent perimeter corners and local trim walks. Exact narrow-phase tests and source order remain authoritative. | `spatial_bounds.gd`; RoadPieceWork `prepare`; PlacedObjectBatches `_prepare_baked_groups`; SplineBorders `rounded` |
| T10 | A 64 MiB estimated retention target covers history, compiled/raster data, road CPU/GPU caches, prop/model caches, detached scenes, document reads/encoding, thumbnails, roadside boundaries, canvas data and prepared race worlds. Reclamation proceeds from inexpensive idle caches toward expensive reusable geometry. OS memory warnings request stronger trimming. Shared scene resources are counted once across active, nested replacement and detached owners. | `editor_memory.gd`; EditorWorld `memory_snapshot`, `trim_cache`; cache trim/residency methods |
| T11 | Baked roles are derived from the actual material family, including Winter craft, instead of merging craft into generic opaque props. Individual soft-object previews discard contact shadows already supplied by outer spatial batches. | PlacedObjectBatches `refresh`, `_prepare_baked_groups` |

History snapshots and derived-state caches are session implementation details. They do not enter serialized or published documents. A long sequence of distinct large paint revisions can retain fewer than forty steps under the byte allowance. During a gesture, the previous stack arrays remain temporarily reserved for exact pinch rollback; memory telemetry includes those references.

The T07 writer ordering also preserves an older **committed** revision when a newer, uncommitted drag has already changed the live dictionary. Its analysis can still save recovery data without applying derived fields over the newer gesture. Pinch cancellation queues analysis for the restored committed state. Write failures stay visible; a successful WIP write does not erase an outstanding original-save failure. Injectable TrackLibrary subclasses retain the existing synchronous fault-test path.

T09 intentionally keeps the existing endpoint-bucket implementation. An unordered-pair prototype did not show a reliable improvement and was reverted. A dense topology that actually contains quadratic numbers of partners still requires quadratic output. The existing selected-piece topology cache from T03 avoids rebuilding that output on every handle query. Dense overlapping geometry and the existing polygon simplifier still have expensive worst cases.

The memory target governs **retained estimates**, not process RSS or Android PSS. Active scenes, pending authoring snapshots, worker intermediates, engine/driver allocations and immutable game assets can exceed it. `memory_snapshot()` separates scene ownership and avoids counting a reused mesh twice. Trimming never joins a geometry worker in an input or OS memory-notification callback; worker-owned data waits for a safe turn. Cache contents can repopulate, so this is a pressure policy and telemetry rather than an out-of-memory guarantee.

## Measurements

The paired synthetic checks execute the captured old operation and the replacement in one desktop process. These are Godot static-allocation deltas and script timings, not phone FPS, input-hardware latency or RSS measurements. The table uses the final headless paired run unless another scope is stated; timings vary between repeats. Raw rows for each renderer are in [the evidence directory](evidence/editor-t05-t11-2026-10-23/).

| Scenario | Before | After | Scope |
| --- | --- | --- | --- |
| Forty maximum-paint states, with unchanged paint between revisions | 111,231,896 additional static bytes | 632,896 additional static bytes | About 99.4% less allocation in this sharing case; distinct paint revisions are separately checked against the 8 MiB bound. |
| Pan begin/end on the 16,384-point paint fixture | 5.384 ms per begin | 0.0029 ms | Navigation never takes a full authoring snapshot. |
| Rounded 512-corner fixture | 88.968 ms | 45.595 ms | Exact output matches the captured algorithm; remaining simplification work is included. |
| Twenty ordinary four-piece edit callbacks | See raw rows | Sub-millisecond handlers in the focused runs | Includes history capture and enqueue, with no synchronous WIP/journal write. This is not a paired comparison with the audit's different 96-piece button fixture. |
| Grouped authored props | Original Winter geometry mismatch; duplicate barrel shadow found graphically | Exact triangles and zero pixel differences under the same cosmetic time and light rig | Pine, Desert, Winter and Night kits; the Winter-available subset and a post-trim rebuild are also checked. |

Cold preparation remains significant. An initial Compatibility trial spent 12.869 s in material warm-up; that trial still contained the subsequently removed omni light. Later warm repeats were about 0.49-0.64 s. A first desktop Mobile trial took 2.558 s and a warm repeat about 0.109 s. Cache state differs, so these are **not** a paired speedup or a final-source cold-start guarantee. Individual driver calls can exceed the cooperative budget. Godot documents that Compatibility needs actual loading-time draws and does not support the Mobile/Forward+ pipeline-precompilation mechanisms. [Godot shader compilation guidance](https://docs.godotengine.org/en/stable/tutorials/performance/pipeline_compilations.html).

Existing large-track checks still report multi-second final detail preparation. The changes reduce input-path work and retained duplication; they do not certify 60 FPS editing on the OnePlus Nord 2 5G.
