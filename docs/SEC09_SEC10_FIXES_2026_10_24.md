## SEC09: bound connections before request dispatch

[`bmt_backend.http_server`](../backend/bmt_backend/http_server.py) extends the locked Uvicorn 0.54.0 h11 protocol lifecycle, retaining its parser. Each accepted connection has an absolute **two-second** first-header deadline. Partial subsequent headers, including a buffered pipelined request, have the same deadline. Sending occasional bytes cannot renew it. Incomplete headers retain a **16 KiB** parser buffer limit.

At most **eight inactive connections** are retained per HTTP process. A new connection closes the oldest inactive one and releases its concurrency allowance synchronously. This leaves room within the existing 24-connection allowance for a complete request even while incomplete heads or empty keep-alive sockets are held. Empty keep-alive also retains Uvicorn's five-second timeout. Active bodies and responses are excluded from eviction and the header timer; the existing ASGI body size, receiver and time limits still apply. The launcher rejects fewer than 16 concurrency slots or a keep-alive outside 1–5 seconds.

The Docker default, production/PC API and private Studio Compose commands, development launcher, isolated Compose smoke command, Google initial deployment and retained updater all select this entry point. The retained updater explicitly replaces command/arguments as well as the image, because an existing Cloud Run command override can otherwise keep selecting raw Uvicorn. No dependencies were added; h11 and Uvicorn remain at their existing lock versions.

Real TCP tests compare original and guarded listeners on owned loopback fixtures. Holding 23 partial heads makes the original return health **503/503/503** and normal authentication **503**. The repaired listener returns health **200/200/200** and authentication **201**, and closes the held connections. Other tests exercise zero-byte sockets, byte dripping, idle persistent sockets, subsequent/pipelined partial heads, malformed/oversized incomplete heads, a 2.3-second active response and a valid upload whose body takes longer than the header deadline.

The two-second deadline and eight inactive slots are deliberate admission limits: a very slow request head can be closed, and a burst can displace the oldest inactive socket. These tests establish the local server behavior, not resistance to arbitrary connection floods or Google/NAS edge acceptance. Keep the existing private listener/proxy topology and calibrate the limits against actual proxy/device connections during rollout.

## SEC10: validate effective grants against the provisioning policy

[`database_privileges.py`](../backend/bmt_backend/database_privileges.py) now shares `relation_policy()` between grant provisioning and production runtime verification. The check is read-only and includes effective PUBLIC grants and column permissions. It rejects:

- Database/schema CREATE, object ownership, role inheritance/elevation and delegated schema access.
- Unexpected or missing table/column privileges, grant options and non-CRUD rights such as TRUNCATE, REFERENCES, TRIGGER and PostgreSQL 17 MAINTAIN.
- Sequence UPDATE/delegation or permissions outside reviewed attached sequences.
- Unexpected function execution/delegation, with explicit helper/trigger signatures, actual pg_trgm extension membership and the narrowly scoped worker audit-redaction function.
- Effective access to unrelated persistent schemas and unknown application relations.

The intended existing workload permissions remain: workers can activate scheduled configuration through the selected columns and append audit rows; private Studio can read the approved identity columns and revoke session families. The audit-redaction function remains worker-only with its exact signature and fixed search path. New tables, views, functions and unattached sequences require explicit provisioning review. A future function with no effective execution grant conveys no runtime authority. PostgreSQL temporary/system facilities are outside this persistent application-object policy.

The guard retains its existing activation condition: production PostgreSQL API/worker/admin workloads. Development mode and SQLite do not claim this production credential validation. Runtime startup rejects drift; an owner/migrator must review and reapply grants separately. Startup never silently repairs permissions.

Disposable PostgreSQL tests cover all three valid roles and actual required worker/admin operations, 22 table/column/schema/function/sequence drift variants, database CREATE, three unreviewed-object variants and the two original-method controls. Both task-original checker controls accept the reproduced schema CREATE/staff UPDATE drift; the repaired checker rejects it. A rejection test confirms the checker leaves the offending grant unchanged.
