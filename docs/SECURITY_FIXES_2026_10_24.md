# Security fixes: SEC06, SEC07, SEC03, SEC08 and SEC04

The five requested findings from [the review](SECURITY_REVIEW_2026_10_24.md) are fixed in source, client behavior, migration and deployment templates. **The later [24October cloud deployment](SECURITY_DEPLOYMENT_2026_10_24.md) activates the backend fixes; PC/client rollout remains pending.** This report records the implementation checkpoint before that deployment. Existing game/editor processes, PC backend containers and cloud services were left running unchanged. No device, APK, purchase, provider sign-in or production account was used.

| Finding | Result |
| --- | --- |
| SEC06 | Small control-body receivers have a global limit of eight, an anonymous limit of four and a limit of two per network/account. They have a five-second total deadline and a two-second stall deadline. Early HTTP/1 rejection closes the connection. A complete buffered request gets one bounded 20ms admission check when its network's receive slots are occupied. Cancellation and disconnect release receivers. |
| SEC07 | Production rejects legacy Studio keys and disabling MFA. The public API excludes administrative routers and rejects administrative paths before SQL/body work. A separate `create_admin_app` factory requires the admin workload and configured staff audiences. Named allowlisting, verified MFA and staff revocation remain enforced. Studio has a separate loopback Compose service/profile and an optional IAM-private Cloud Run service. |
| SEC03 | Both appearance writers check the current account's permanent cosmetic unlocks while holding the player write lock, including equal-value retries. Other players' grants and client-supplied previous values cannot authorize a selection. Signed-in client ownership ignores local legacy lists. Rejection preserves the local design and pending edit and explains the account requirement. |
| SEC08 | API, worker and Studio use different database users and credentials; production schema ownership belongs to the migrator. Compose separates environment secrets; cloud plans separate service accounts and secret grants. Workers cannot read identity/token tables or staff records, change policy contents, rewrite/delete administrative audit records or perform schema DDL. Child processes discard administration credentials. |
| SEC04 | The unproved ad-preview bridge defaults off, requires explicit development/test opt-in, and is rejected in production configuration. Production advertises no preview. Daily, banked and ad-free resumes and three purpose-bound Circuit resumes retain their existing rules. |

Migration `0061_security_authority`, following the concurrent `0060_game_configuration`, grants only known selections already stored in nondeleted server player profiles. It uses 200-player keyset batches, zero-price permanent grants and conflict-safe inserts that preserve purchase history. It never ingests a client's legacy list or converts a future first write into ownership. Unsynced historical local designs remain available offline; authenticated sharing requires account ownership. The downgrade deliberately retains permanent grants. Do not roll back to an appearance writer that lacks enforcement.

The database policy enumerates reviewed tables, clears stale table/column/function/default grants, refuses privileged/inheriting/object-owning runtime roles, and rejects unreviewed tables. New tables receive no automatic runtime CRUD. The worker retains required game-domain writes and may append scheduler audit entries and update only activation metadata for already published schedules. Account deletion uses a fixed-schema, fixed-search-path definer function that redacts only private audit fields after an account tombstone; command, actor, action and request provenance remain intact. This contains credential and administrative authority exposure; a compromised verification worker still has substantial trusted game/reward authority.

The concurrent `0062_retire_discovery_cache` is preserved and is outside this change. Runtime grants tolerate the absence of those retired cache tables. The ranking router and public game-configuration routes are retained in their appropriate services.

Production runtime startup also rejects schema-owner, elevated, excess or mismatched workload credentials. This prevents an image-only restart from silently retaining the former shared database authority.

## Rollout requirements

1. Back up and quiesce all writers, including Studio. Drain accepted verification/publication work. Run the cosmetic cutover while old appearance writers are stopped so the server-stored grandfathering snapshot has a clear boundary. Deploy matching API, worker, migrator and client sources. Keep the current migration chain, including concurrent migrations.
2. Use four distinct database credentials. Fresh production Compose volumes initialize `bmt_migrator`, `bmt_api`, `bmt_worker` and `bmt_admin`; `migrate` runs `python -m bmt_backend.database_privileges --migrate`. `init_env.py` generates separate random values. The schema-owning migrator is a non-superuser; ordinary services never receive its password. PC development preserves its existing database/admin credential for the DB/migration service only and provisions separate runtime roles on the next explicitly requested BackendStart.
3. Existing production volumes do not rerun `init-db.sh`. An owner must create the new roles with private interactive password handling, transfer the dedicated application's existing schema/table/function ownership from the old app role to the migrator, remove elevated runtime attributes/memberships, then apply migrations and `database_privileges.configure`. Inventory ownership first; never reassign a shared database blindly. Disable the former shared role's login and retire its credentials/connections after all old workloads drain. Grants alone cannot restrict a table owner. The grant tool refuses such an unsafe layout.
4. Fresh cloud plans use `bmt_api`, `bmt_worker`, `bmt_admin`, a new API service account/API secret name, and dedicated worker/Studio service accounts and secrets. The migrator alone receives the PostgreSQL administrator secret. Existing retained cloud deployments require an explicit authority cutover: provision/bind the new roles and secrets, remove old IAM secret grants, retire the former shared SQL login and service identity, and preserve the existing staging ownership guard. `update.py` refuses image-only rollout until the exact separate service-account, secret and workload bindings are present. This task did not provision those resources or rewrite existing secrets.
5. Production Studio is an optional `studio` Compose profile on loopback8081 (PC18182), or `admin_enabled` Cloud Run service with `--no-allow-unauthenticated`. Do not route its port through the public game proxy. Configure a private staff access path, exact staff audiences/subjects, and provider tokens carrying verified MFA claims; test named sign-in, revocation and audit attribution before enabling it. Cloud IAM invocation and application staff authentication are separate checks. The tested provider is a local verifier fixture; real provider/MFA acceptance remains an owner rollout check.
6. Leave `BMT_TEMPORARY_AD_RESUMES_ENABLED=false` for production. A future rewarded-ad service needs authoritative receipt verification; flipping a client or Studio advertising flag does not authorize free server resumes. The explicit local preview flag is for development/test only.

Local implementation/testing is complete. Matching rollout, private staff access/provider acceptance and live operational calibration remain separate work. Existing instances retain their previous behavior until that rollout.
