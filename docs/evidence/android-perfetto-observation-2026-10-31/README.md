# Isolated Android Compatibility trace — 31 October 2026

This supplementary trace was recorded on the authorized OPD2403 tablet **after** the primary renderer comparison, using the separately installed, offline `org.beatmytrack.rendererprobe.gl20261031` package. The app and driver caches had already been exercised; this is not a fresh-cache result or a matched renderer comparison. The release probe is `profileable` by shell, is not the production package, and stores its records privately. The trace was started before the isolated activity launch; the game probe then waited at its own gate before its App was instantiated. No cache was cleared and no production app was stopped or altered.

## Scope and important limitations

- Perfetto ran for 120 seconds, with 16 MiB and 32 MiB discard-mode buffers, PID/command-line-scoped 99 Hz native sampling, scheduler/CPU frequency events, app-specific atrace tags and FrameTimeline. A separate approximately one-second poll recorded the owned SurfaceView's SurfaceFlinger latency ring. The recorder consumes CPU and memory and can perturb timing.
- **No CPU samples were captured**: `perf_sample` contained zero rows for the entire trace and `perf_session` was empty. The trace's process entry for PID 6014 had the exact configured package command line. Scheduler records show that process executed on CPU during the captured prefix, so zero samples do not mean zero work. The sampling buffer had no recorded discards or patch failures. There are no nonzero Perfetto `perf_*` error counters. The later capability check below found `linux.perf` registered and recorded stackless samples for an independent shell workload. Why this app trace had no samples is **unproven**.
- The scheduler/ftrace buffer filled: `traced_buf_chunks_discarded[1]=2853` and `traced_buf_patches_failed[1]=2846`. Captured scheduler rows cover approximately the first 34.1 seconds, not the full 120 seconds. Consequently this is not a complete scheduler profile.
- Perfetto service query advertised `android.gpu.memory` but no render-stage source; kernel trace-event listing was denied and no GPU frequency/memory ftrace events were enabled. `gpu_slice` has zero rows. Generic GPU-named counters in the trace are not a measurement of this app's GPU execution time. `actual_frame_timeline_slice` contains 24 app-associated rows, but SurfaceView coverage is not established. See [Perfetto's FrameTimeline documentation](https://perfetto.dev/docs/data-sources/frametimeline).
- There was no second tap during loading, so this run does not measure input acknowledgement or input-to-photon latency. Time-sampled CPU stacks, had they been available, would still not directly measure an individual GL call's wall duration.

## Observations

The probe log identifies the selected renderer as Compatibility and records a 6,204 ms App-startup stage with a 4,867 ms maximum engine callback interval. Its first Star race loading stage recorded 20,255 ms and a 242 ms maximum callback interval; the same-process repeat recorded 9,400 ms and a 144 ms maximum. The fixture compilation precedes those load-stage timings. These are instrumented, cache-warm diagnostic observations; they do not explain the cause of the long startup callback or measure a cold process's earliest startup work.

All 109 SurfaceView ring polls succeeded; maximum host time between polls was 1.172 s. The analysis found 5,575 distinct valid second-column timestamps. Device REALTIME and MONOTONIC-to-trace clock-offset ranges were each 156 ns across recorded snapshots, and 5,420/5,575 mapped timestamps fell within the trace interval. Using approximate epoch-logcat phase markers, the startup interval contained a 4,829.782 ms gap between valid ring timestamps; both endpoints appear in three individual poll responses. The first Star load had a 219.988 ms maximum mapped ring gap, and the repeat 119.993 ms. The startup gap is consistent with the long callback, but pending/invalid ring rows, OEM timestamp semantics and approximate boundaries prevent treating it as a verified hardware-present or photon-latency measurement. A ring gap is not a shader-link attribution.
