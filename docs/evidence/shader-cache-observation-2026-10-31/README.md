# Compatibility shader-cache observations — 31 October 2026

This is a passive desktop diagnostic, not a production engine change, an Android measurement or a cache-coalescing implementation. It uses the same owned-process GL function-pointer observation technique as the earlier native study. The diagnostic changes no GL call arguments or return values. The private process uses isolated application data and makes no live-account requests. The owner’s running processes are not instrumented.

## Result

In the interval **after the diagnostic extension loaded and before it unloaded**, there were 445 `glGetProgramBinary` calls requesting 75,388,233 bytes in aggregate. Their measured CPU-call durations totalled 50.743 ms, with a maximum of 0.469 ms. Of these, 256 calls were the second or later extraction of the same process-local program handle between observed deletions: 46,804,231 requested bytes and 30.619 ms summed CPU-call time. There were 445 `GL_PROGRAM_BINARY_LENGTH` queries totalling 1.128 ms, with a maximum of 0.132 ms. All observed operations ran on one thread. `glProgramBinary` import had 18 calls totalling 18.495 ms. All **1,105 bounded events** were captured, with none dropped.

The first race's longest observed App callback interval was 7,729.198 ms; approximate event-clock overlap is 8.370 ms of binary extraction plus 0.133 ms of binary-length queries. That makes the measured extraction calls a small fraction of that interval in this observation. **It does not attribute the remaining time**: compile/link, setup and filesystem writes were not hooked. The log status label `Preparing start…` is not a cause. The Windows Compatibility run cannot establish Android behavior.

These events support the narrow finding that repeated extraction happens. They do **not** prove the potential time saved by coalescing: a coalesced implementation might persist a different set of binaries, delay cache creation, retain different data, or move work to a later interval. The underlying engine can also write each binary to disk, which this trace does not measure. Godot passes a null returned-length pointer to its extraction call, so byte counts are the requested buffer sizes, not independently verified actual bytes.

The trace process's first/repeat App load observations were 54.849/2.671 s with 7,729/171 ms maximum callback intervals. A subsequent uninstrumented fresh-profile control observed 56.806/2.870 s and 7,830/202 ms. Both engine processes exited zero and each checked 10 assertions with zero failures. Driver/OS caches were not cleared, the runs were sequential, and host activity differed; these do not measure instrumentation overhead or establish a speedup. Callback intervals are not display presentation intervals.

## Boundaries and retained failure

- `trace.json` contains raw event rows `[kind, thread ID, program handle, requested/reported bytes, UTC start µs, CPU-call duration µs]`; kinds 1–4 are binary-length query, extraction, import and program deletion. A handle is process/context local and is not a source hash. The 189 inferred handle lifetimes use observed deletion calls; earlier activity before extension initialization is outside scope.
- `frame-spans.json` holds App callback intervals only while the fixture records race loading. Trace-to-frame overlap uses separately calibrated wall clocks and is approximate.
- The extension was loaded into the exact Windows engine executable with SHA-256 `ab1824f85bfd8e0e4128182c000c4003a3e042245b2967848d089b2a04b22424`; the measured diagnostic DLL SHA-256 was `d8a83b87315ad31339804b29951bc9a14d3f024411ebd1040a27e2d5c32a71e1`. Its source SHA-256 is `cc68b97b662c7cd132cb097d7e7b004845e21d9f75f808846bf35b82b951f871`; the included helper header is `40c97d329edce171d472fbe83c1b07be09911d24fb9bf0861f196558fca2b0ed`.
- The extension's teardown code restores slots still pointing to its own hooks, but this v1 run did **not** independently count restored slots. Process termination releases its address space. The trace records `installed=true` and zero dropped events, and the engine exited zero.
- The original trace runner returned **exit 1** because it searched GUI-executable stdout, which was empty. The private `godot.log` and load-profile JSON independently record `RUNTIME_PROFILE: 10 checks, 0 failures`, and the recorded child exit was zero. `trace-execution.json` retains the false-negative. The archived runner includes the subsequent fix to inspect the private Godot log; it was used successfully for the uninstrumented control.
- Windows emitted the offline root-certificate-store error. The event recorder has fixed 32,768-event storage and records every cache call; its cost is not independently quantified. The engine/window/driver retained their normal configuration; no `glFinish()` was added.

`cache_trace.cpp`, `shader_job.hpp`, the generated profile and runner are retained as source context.
