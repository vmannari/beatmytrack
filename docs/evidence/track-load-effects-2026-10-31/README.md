# Covered effects draw diagnostic — 31 October 2026

An offline actual-App Star fixture measured the effect preparation phase on Godot 4.7.2 Compatibility, Windows, RTX 3090, 1280 × 720 and Dummy audio. It used fresh private App and road data. OS and driver caches were not cleared. Track compilation occurred before the timed race, selection prefetch was bypassed, and neither network nor Android was tested. The results are wall-clock intervals, not native GPU or driver timings.

The first race took 53,404.339 ms, including 31,514.211 ms for world graphics preparation and 9,556.071 ms for combined effects, final draw and cleanup. The repeat took 2,280.939 ms, including 351.593 ms for that combined effects phase. The first run staged 20 particle proxy draws; their waits summed to 9,512.190 ms. Dust0's first draw waited 7,506.570 ms; TyreDust0 561.987 ms; Clippings0 582.647 ms; Smoke0 305.124 ms; Spray0 287.073 ms. The remaining individual waits were 7–30 ms. On the repeat all 20 proxies were reused, their draw waits summed to 298.896 ms, and each was about 13–15 ms.

The draw sequence was Dust0, TyreDust0, Clippings0, Smoke0, then the same four families for indices 1, 2 and 3, followed by Spray0, Mud0, Spray1 and Mud1. A draw is a frame containing more than that named proxy: the already visible world and car, as well as applicable finish, trail, bridge/hazard and impact-canvas preparation, can also contribute. Therefore the Dust0 interval is not evidence that Dust0 or its shader alone caused the delay. Awaited frame pacing also contributes to the repeat waits. Reused proxy nodes are reconfigured for each source; matching names are not proof of equivalent programs or graphics contexts. Further isolation and first-emission, visual, cancellation, memory-pressure and context-loss checks are needed before coalescing or skipping draws.

The new [probe](../../../game/tests/profile_effect_load_stages.gd) extends the existing stage profiler and changes in-memory script copies only; it retains draw order and production behavior. [Compatibility log](compat.log) contains per-proxy rows and the [timing JSON](timings.json) contains the broader stages. The graphical run exited 0; the offline process reported the Windows certificate-store warning. A separate headless smoke run exited 0; its [log](headless.log) is not a graphics measurement. ## Exploratory repeat batching

A separate [diagnostic experiment](../../../game/tests/profile_effect_batch_experiment.gd) retained the original cold path and only grouped reused proxies when all source emitter configuration, process-material and draw-mesh resources serialized to the same digest. It still submitted every proxy in its group and waited for an actual covered draw before marking the group initialized. If any source was absent from the pool, it used singleton groups. The grouping changed only in-memory copies of the App and effects scripts; no runtime implementation was shipped.

The 20 Star proxies formed six groups of 4, 4, 4, 4, 2 and 2. In one private-process run the warm control effects spans were 350.250 and 408.495 ms, bracketing a 126.665 ms experimental span; complete race times were 1,502.939 and 1,840.654 ms versus 1,439.340 ms. A second run with the same private application/driver cache measured controls of 344.818 and 343.917 ms versus 121.051 ms experimentally; corresponding whole-race times were 1,456.132 and 1,647.496 ms versus 1,394.389 ms. These are small samples on one shared Windows machine, and do not establish a stable end-to-end or Android gain. The first run's untouched cold path took 53,179.586 ms; this proposal does not address its 9,687.984 ms cold effects span.

Each race then exercised all 20 live emitters for three actual draw frames. Captured canonical state stayed exact; the three frame waits were roughly 16/8/8 ms for both control and experimental cases. Navigation cancellation and an OS memory-warning interruption were also injected during an actual multi-proxy draw. Cancellation left no active game or loading overlay; pressure completed the race and left the preparation pool at zero accounted bytes. These checks do not establish visual equivalence, context-loss safety, all car/theme behavior or absence of later hitches. The first run's exit reported five leaked ObjectDB instances and one resource. The diagnostic then explicitly released its own App, script and track references and allowed eight cleanup frames; the verbose lifecycle repeat reported no leak warning. That suggests a fixture-lifetime issue but is not a long-session leak test. Windows certificate-store errors were also logged.

The serialized digest is intentionally diagnostic and is **not bounded for production**: it can traverse large resource graphs and allocate serialized data, and it does not establish every renderer/driver condition. A more conservative resource-identity inventory found **20 distinct process materials, 20 distinct meshes and 20 distinct surface materials** among 20 emitters, despite just four shared shader objects. Thus a key requiring all those identities would yield singleton groups and no benefit. Shader identity alone is unsafe: for example, Dust and TyreDust share the shader while using different process and mesh configuration. The independently mutable process and material wrappers are deliberate in `sand_dust.gd`; sharing them to force a hit could leak live settings. This experiment is not selected for production.
