# Isolated Android renderer comparison

This is a diagnostic harness, not a renderer recommendation or an Android performance result. It creates private copies under `build/android-renderer-comparison-20261031`; it never changes the root project, owner saves, app package, or device by itself. `prepare.py`, `finalize_common.py` and `build_pair.py` do not call ADB. `collect.py` only reads the foreground activity, the probe's PID-scoped logcat and SurfaceFlinger; it never installs, launches, wakes, injects input, force-stops, clears or uninstalls anything.

The connected device was observed awake with the owner's production game in the foreground on 31 October 2026. Do not launch a probe until the owner has finished that session and an appropriate device window is available. Check the foreground again immediately before any later device action.

## Build setup

From the repository root, with pinned Godot 4.7.2, Android templates, SDK/JDK and the repository's pinned Android source template available:

1. Run `python tools/android_renderer_comparison/prepare.py`. It refuses to overwrite an existing task directory and records hashes for the common source snapshot. The workspace may change while copying, so separately audit the hash ledger against the intended source snapshot. Both variants use the same private source copy and content; package ID and renderer/project feature differ. The fixture is the same Star document.
2. The normal Garage preview integrity check must pass. If it reports stale previews, run the existing `scripts/bake_garage_previews.gd` once in the **private common snapshot** with pinned Godot and a graphical renderer, then run `python tools/android_renderer_comparison/finalize_common.py`. This verifies the snapshot and both variants and copies the same native output to each. Do not bypass the gate or bake into the owner's project.
3. Run `python tools/android_renderer_comparison/build_pair.py`. It uses a private signing key, Godot user directories, Gradle cache and scratch directory. The repository's `scripts/run_no_crash_dialog.py` wraps the entire noninteractive PowerShell runner, including its Godot version check. The task-only Gradle wrapper uses offline mode; the private manifest requests removal of INTERNET, and the final APK must pass `aapt` checks for its package ID, no INTERNET and non-debuggable status. A failed import, export or check is a failure, not an APK acceptance. `--only compatibility --max-seconds 600` selects one variant with an explicit 600-second outer bound. Independently run `audit_imports.py <private-project>/game --out <new-report.json>` after import; any stale, missing or unverified import must be resolved before using an APK. Run `compare_variants.py` after both builds to detect unexpected source-tree differences; this does not prove APK contents or runtime visual parity.

The initial preparation on 31 October copied existing root `.godot/imported` data and the owner's Gradle `modules-2`/wrapper distributions into task-local caches; it did not modify the originals. This was a cache-seeded experiment, not a clean import. Its source/output checksum audit found 1,125 matches and five stale preview imports before reimport. The private import and independent post-import audit must both pass; do not assume the cached outputs are valid. The runner no longer copies the owner's Gradle cache; an independently provisioned private offline Gradle cache is required. The sandbox attempt and subsequent locked-DLL/240-second timeout attempts are retained in the task directory.

The isolated package IDs are `org.beatmytrack.rendererprobe.gl20261031` and `org.beatmytrack.rendererprobe.vk20261031`. They do not replace `org.circuit01.handlinglab`. Installing or launching them still changes the connected device and can interrupt its foreground app. The build setup performs neither operation.

After both builds, `compare_apks.py <compatibility.apk> <mobile.apk> --out <new-report.json>` compares the uncompressed packaged `assets/` and `lib/` content, allowing only the generated project configuration and build identity to differ. It flags other differences for investigation. This check excludes Android manifests, signatures and Gradle metadata; verify those separately and do not infer runtime renderer choice or pixel parity from byte equality.

The 31 October artifacts **do not pass this strict comparison and are not yet a controlled timing pair**. Four exported scenes differ in serialized node IDs; the sparse-pack index and baseline profile reflect changed content and DEX checksums. `apk-content-comparison.json`, `apk-difference-explanation.json` and `scene-comparison/scene-state.log` retain the failure and the byte-level and scene-state investigations. Semantic inspection is not proof of identical runtime behavior. The manifest comparison normalizes identity and renderer fields; the Mobile manifest additionally declares optional Vulkan level/version features. Both builds are non-debuggable, arm64, target SDK 36, minimum SDK 24, without INTERNET, and share the task-only signing certificate.

The independently generated build identities also have different per-car Garage and header preview revisions. These revisions feed cache keys, and the Compact header template rejects a mismatched embedded revision; paint icons key on the full build ID. Pinned Godot inspection of the two private Compact templates found embedded revision `c13110e0cf58323c85c2cbb0a604b5a516537234a0d80dbd21390025f59535d4`; Compatibility and Mobile generated revisions are respectively `add4974ad70afd481826181703910ea034f5350732dde0590f86641167ccd0c0` and `a9573e4aeb5339a05a98c9eff13c1627ce24cce7d68361bf6c5757fe087f27ed`. Both fail that revision guard, although other cache-hit parity and device runtime behavior have not been demonstrated. `template_revision_probe.gd` in the task directory records the inspection method. Before collecting comparative timings, align or explicitly validate the full cache/template behavior without bypassing safety guards, rebuild, repeat the import and package audits, and verify actual renderer and visuals. The two existing APKs are retained as diagnostic evidence only.

`run_template_probe.py` saves the two wrapped Godot runs and their successful exit codes as `compatibility-template-revision-probe.log` and `mobile-template-revision-probe.log` in the task directory; both runs also record the sandbox root-certificate warning. The template file inside each APK and the corresponding inspected source file all have SHA-256 `f5ed4354cc15048cbf50a0b10b6774d6ecf8ebef2b817eedb0a1feef70f39fde`. This demonstrates one exact revision mismatch on both sides, not actual runtime hits or misses for the other caches.

## Collection and interpretation

After an isolated package is deliberately installed and launched during an appropriate test window, it waits on a tap-to-start screen. Attach the collector **before** tapping:

```powershell
python tools/android_renderer_comparison/collect.py --adb 'C:/Users/ville/AppData/Local/Android/Sdk/platform-tools/adb.exe' --serial '<test-serial>' --package org.beatmytrack.rendererprobe.gl20261031 --out build/android-renderer-comparison-20261031/collect-gl
```

Wait for the repeated `BMT_PERF_GATE_READY` entry to appear in `observations.jsonl`, then tap the task-owned probe. Use a fresh output directory and the corresponding `vk...` package for Mobile. The probe records the actual renderer returned by `RenderingServer.get_current_rendering_method()`; a fallback to Compatibility invalidates a Vulkan comparison. It emits requested renderer, device and engine details, phase markers, application frame intervals, race preparation stages, first driving windows and touch-receipt timestamps. The gate separates **process launch** from **gated App startup**; process-launch time and any shaders prepared for the gate are outside that startup phase. Logs of touch receipt do not measure physical input or touch-to-photon latency, and no automated loading-input acknowledgement is currently implemented.

The collector stores every raw SurfaceFlinger response, layer lookup, host poll timestamp/gap and a final poll at each observed phase end, including loading. It stops collecting if the probe is no longer the top resumed activity. The app's timestamps, logcat marker arrival and SurfaceFlinger presentation timestamps are not automatically on a common clock. SurfaceFlinger's ring can overwrite samples, and attachment or layer discovery can miss boundaries. Therefore a measured maximum is only an **observed lower bound** unless first and last frame coverage and clock mapping are independently established. Unsupported/missing layers, missing gate markers, poll gaps, fallback renderer, incomplete phases and the device refresh mode must be disclosed; do not convert application callbacks into claimed presented-frame or physical-input timings. This harness does not trace native GL/Vulkan compilation, binary-cache operations, GPU execution or driver memory; it cannot attribute a stall to a driver function.

Use matching production visual settings, car, track, input and test duration. Collect first and repeat loads, first real driving/effects, memory and thermal data on both renderer variants. Alternate runs where practical and retain every failure. A fresh app package does not clear or prove a cold driver cache. Validate visual fidelity and compare actual matched settings before choosing a renderer.

`python tools/android_renderer_comparison/test_collect.py` runs a simulated offline collector check. It does not validate an Android SurfaceFlinger implementation, export, device behavior, frame coverage or latency.

For future builds, the probe builder leaves the stock driver in place during countdown and waits until simulation tick 10 before assigning the automated driver. The game still applies its normal launch rules: tick 10 is the first tick outside its early-throttle penalty window. The report records takeover countdown and tick, first automated sample tick, prior early-input flag, launch result and delay. It does not guarantee that a separate real touch or other input cannot cause an early start. The existing 31 October APKs and recorded runs predate this change; their primary false-start status remains unknown. `python tools/android_renderer_comparison/test_prepare_driver.py` checks the actual archived-probe transformation and fail-closed behavior. `test_driver_start.gd` checks the real launch state and rules with safe and early-throttle controls using pinned Godot; Android validation is still required for any future rebuilt APK.

## Offline review of a completed collection

`analyze_capture.py` reads saved JSONL only; it does not invoke ADB. Wait for the collector's final `end` record, then use a **new** output path:

```powershell
python tools/android_renderer_comparison/analyze_capture.py build/android-renderer-comparison-20261031/device-gl/observations.jsonl --second build/android-renderer-comparison-20261031/device-vk/observations.jsonl --apk-audit build/android-renderer-comparison-20261031/apk-content-comparison.json --first-template-check build/android-renderer-comparison-20261031/compatibility-template-revision-probe.log --second-template-check build/android-renderer-comparison-20261031/mobile-template-revision-probe.log --out build/android-renderer-comparison-20261031/analysis-new.json
```

For a single collection omit `--second`, the APK audit and the second template check. The analyzer hashes input JSONL, decodes the complete numbered report chunks, checks actual renderer and gate/case markers, and records absent or conflicting evidence. Its `global_observed_edges` deduplicates only adjacent valid actual-present timestamps found together in one SurfaceFlinger ring dump; it does not manufacture a gap between separate dumps or across invalid timestamp rows. `by_poll_phase_not_clock_aligned` is **not** a strict per-phase presentation series: poll-phase labels use received log markers, while ring data may predate those markers. The observed maximum is not a certified maximum when frame/boundary coverage is incomplete. Nonoverlapping successive dumps, unsupported layers and poll gaps remain visible, and no clock synchronisation is assumed. The analyzer always marks controlled comparison as unestablished because package content, runtime cache behavior, matching visual state and device coverage require separate evidence. `test_analyze_capture.py` tests its offline parsing and failure handling with synthetic data; it is not device validation.

The current probe does **not** record effective MSAA or whether `mobile_world_aa` is active. This matters on Adreno Android: Compatibility can replace MSAA with its post-world FXAA path while Mobile/Vulkan retains another AA configuration. Matching project settings alone does not prove equivalent rendered quality or workload. Its reported viewport/render scale, selected renderer, car and track phase are useful observations, but do not prove matching sky/effects, draw calls or imported resources. The gate occurs after process startup and can prewarm its own rendering resources. The 720-second probe deadline starts before the gate is tapped, so a long gate wait reduces time available for cases. App phase-end timing and later logcat/SurfaceFlinger polling also do not establish physical touch-to-photon latency.

The collector has no screenshot, PSS, thermal, energy, GPU or native driver-call capture. For a later visual-specific pass, capture only while the isolated probe is verified foreground; use matching device mode, display resolution, car, appearance, camera, track content, simulation tick and first-use state. A separate held-pose or explicitly synchronised capture scenario is needed: the current moving route and diagnostic banner do not provide matched camera/tick screenshots. Compare repeated same-renderer captures first to understand noise, then inspect cross-renderer captures at full resolution with dynamic HUD elements identified separately. Keep unmasked images and any masks and calculations; a global pixel difference cannot by itself identify a defect, and a mask can hide one. Inspect cars/outlines, all five biomes, headlights, transparent particles, wet surfaces and reflections before accepting Mobile. Do not collect another app's screen or treat screenshot capture as a timing-neutral operation.

### Clock-domain investigation

The current collector requests `logcat -v raw`, which deliberately omits log metadata including its timestamp; adding an interpretation later cannot recover a device-clock phase time from the saved lines. Android documents `monotonic` as a log-format modifier showing CPU seconds since boot, and `usec` as microsecond **display precision**. A future separate collector could test a timestamp-bearing format such as `-v threadtime -v monotonic -v usec` rather than `raw`. See [Android logcat formats](https://developer.android.com/tools/logcat). Verify the actual device's emitted format and PID filtering; a modifier combined with `raw` is not sufficient to make `raw` print metadata.

AOSP's [FrameTracker dump](https://android.googlesource.com/platform/frameworks/native/+/ee4bf4c9660809e7fb967cccfd6bdcfc67b3b113/services/surfaceflinger/FrameTracker.cpp) writes desired-present, actual-present and frame-ready values in that order; Android's [SyncFence API](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/hardware/SyncFence.java) specifies `CLOCK_MONOTONIC` for fence signal times. These sources make a common-clock correlation **testable**, not proven for every vendor path on this Android 15 device. AOSP log formatting can [convert stored timestamps to monotonic](https://android.googlesource.com/platform/system/logging/+/refs/heads/main-kernel/liblog/logprint.cpp); log-clock configuration, conversion accuracy, suspend, formatting resolution and emission latency need verification. `CLOCK_MONOTONIC` excludes deep sleep; [Android documents its distinction from elapsed realtime](https://developer.android.com/reference/android/os/SystemClock).

Before attributing an interval to a loading phase, a separate isolated experiment should bracket logging with device-side `CLOCK_MONOTONIC`/`SystemClock.uptimeNanos()` readings, validate the log timestamp's conversion and uncertainty repeatedly, verify that the collected layer's actual-present values use the compatible device clock, and record first/last frame coverage and gaps. Emit explicit start **and end** markers: the current `begin()` logs after recording phase start, while `record()` logs after constructing the summary, so their timestamps are not exact boundaries. Conservative analysis can then include only edges proven to lie inside a bounded phase; it still cannot certify a maximum or percentile if presentation ring samples or boundaries are missing. No such device-side validation or timestamped phase stream was performed by the current collector.

For a **future opt-in** run, `collect_timestamped.py` accepts the same arguments and read-only attachment policy as `collect.py`, but asks PID-scoped logcat for `-v threadtime -v monotonic -v usec`. Use it only with a fresh output directory; it did not run for the existing captures. Its `timestamped-format.json` records the requested format, not proof of actual output or clock alignment. The offline analyzer recognizes the expected six-decimal timestamped marker layout and reports any PID mismatch, but a missing recognition means no timestamp claim can be made. Neither the wrapper nor parser validates clock origin, conversion, boundary latency or actual-present clock. They do not assign SurfaceFlinger frames to phases based on those timestamps. Run `python -m unittest discover -s tools/android_renderer_comparison -p 'test_*timestamped.py' -v` for simulated prefix, parser and fail-closed command checks; these do not validate behavior on a device.
